## Overall verdict

The tool is real, not a stub, for its primary use case: SessionStart/SessionEnd hooks for Claude Code actually write, update, and close entries in an atomically-locked JSON registry, and asr/csr actually list, restore, register, prune, and export sessions. Tests exercise real file-locking, atomic-replace, and CLI behavior, not mocked-out no-ops.

However, README's five-agent-fleet framing overstates automation: only Claude Code has a real hook integration (hooks/session-start.py, hooks/session-end.py, wired via Claude Code SessionStart/SessionEnd events). Codex, Cursor, Antigravity, and Hermes support is limited to (a) an --agent field accepted by csr register and (b) resume-command templates in launcher.py and Restore-AgentSessions.ps1. There is no code in this repo that automatically detects or registers a Codex/Cursor/Antigravity/Hermes session - a user (or that agent's own tooling, external to this repo) would have to call csr register --agent codex manually. This should be described as manual registration plus templated resume for four agents, automatic hook-based tracking for Claude Code only.

## PowerShell cmd parity - 2026-11-02

- RESOLVED: `scripts/Restore-AgentSessions.ps1 -Terminal cmd` now writes a unique, exclusively created UTF-8 (no BOM), CRLF `asr-*.cmd` and launches `cmd.exe /k call "<script>"`. Session id, cwd, name and the custom template stay out of the `/k` string. Batch token/text quoting matches the Python launcher; the existing `[AGENT] name` title is preserved.
- Decision: reuse the Python launcher's self-deleting parenthesized batch structure and trusted batch-template semantics. This keeps both entry points consistent without adding dependencies or changing the PowerShell backends. The script removes itself on entry; PowerShell removes it on write/launch failure; dry-run creates no file. As with Python, a malformed trusted custom template (for example an unquoted closing parenthesis) can break the block and leave a file; no broader template rewrite is included.
- Regression evidence: final tests against the original HEAD script (`uv run pytest tests/test_restore_script.py -q -W error --tb=no`) returned exit 1, `7 failed, 4 passed`. Five agent cases rejected inline `/k` session data, and the custom-command/self-deletion and launch-failure cleanup cases failed. The same tests pass with the implementation.
- Tests record Start-Process arguments without opening windows. The Windows-only probe executes the captured `call "<script>"` through real `cmd.exe /c`, with a TEMP path containing spaces and `&`, and checks original arguments/cwd with `%PATH%`, `!`, `&`, `^`, quotes, parentheses, trailing backslash and Chinese text. It verifies self-deletion. The separate interactive-window roadmap item remains open.
- RESOLVED (fixed in 094c3de7, 2026-11-02): second-round security fixes, all found by review of this change, all of the same class (session data reaching a command interpreter as code).
  - CRLF injection in the PowerShell script: the script read the registry JSON directly and skipped the cleaning `models.py` does, so a name such as `x{CR}{LF}calc.exe{CR}{LF}rem` put `calc.exe` on its own batch line (a `{name}` placeholder inside quotes did not help). Fix: `Remove-ControlChars` strips ASCII control characters and DEL from name (falling back to the directory name when nothing is left) and from the agent tag; a cwd containing a control character is skipped with a warning before `Test-Path`; `$SafeIdPattern` and the `ConvertTo-BatchToken` plain-token test end in `\z` instead of `$` (.NET lets `$` match before a trailing newline, Python `fullmatch` does not).
  - The same hole in Python: `SessionEntry.__post_init__` only trimmed `agent`, so an embedded newline reached the cmd `title` line and the `#` comment in `generate_powershell_script`. `agent` is now stripped of control characters like `name` (empty becomes `claude`), and a name that is empty after stripping falls back to the directory name.
  - Unicode single quotes: PowerShell accepts U+2018, U+2019, U+201A and U+201B as single quotes as well, but `quote_powershell` and the script's `ConvertTo-PSLiteral` only doubled the ASCII apostrophe, so a name such as `x{U+2019}; calc.exe; {U+2019}` ended the literal early and ran `calc.exe` (pwsh backend, wt template placeholders, `generate_powershell_script`). Both functions now double all five characters. The earlier claim that single-quoted literals were "simple and complete" was wrong and is corrected above. `custom_resume_cmd` template text itself stays trusted and unrewritten.
- Regression evidence (tests written first and run against the unfixed code): `tests/test_restore_script.py` 7 failed / 14 passed (CRLF name, CRLF in a `{name}` placeholder, agent newline, control-only name, id with trailing newline in three backends; the cwd-with-control-character tests were already green because such a path never passes `Test-Path`, and stay as property checks); `tests/test_models.py` plus `tests/test_launcher.py` 5 failed (agent / name control characters); Unicode quotes 28 failed, plus 7 ASCII-apostrophe baselines that passed (selection `-k "unicode or single_quote"` across `tests/test_quoting.py`, `tests/test_launcher.py`, `tests/test_restore_script.py`). The quote tests use the real PowerShell parser (`Parser::ParseInput`, text is parsed, never run; `tests/_psparse.py`) and assert that no `calc.exe` CommandAst appears, for each of the four Unicode quotes and the ASCII one.
  - Missing call operator (functional): `format_argv_powershell` produced `'claude' '-r' 's-1'`, a quoted string followed by more strings, which both Windows PowerShell 5.1 and PowerShell 7 report as `Unexpected token`; the built-in-agent resume command of the pwsh/powershell/wt backends and of `generate_powershell_script` therefore never ran. It now returns `& 'claude' '-r' 's-1'`. All three callers (`build_resume_command` for wt and for pwsh/powershell, `generate_powershell_script`) embed it in PowerShell text only.
  - Native `wt.exe` call (security): `generate_powershell_script` emitted `wt.exe -w 0 new-tab ... --title '<name>' pwsh ...`. Windows PowerShell 5.1 (and PowerShell 7.2 and earlier) does not escape `"` when passing arguments to a native program, so a name such as `a" pwsh -Command calc.exe "` made wt receive extra arguments after `--title` (reproduced: argv `["--title", "CLAUDE: a", "pwsh", "-Command", "calc.exe", ...]` under 5.1). The script now builds the command line with `subprocess.list2cmdline` and calls `Start-Process wt.exe -ArgumentList '<one string>'`, which passes the string unchanged on every PowerShell version. The non-wt branch had the same flaw in a milder form (an `-ArgumentList` array is joined with bare spaces, so the `-Command` text containing spaces was split), and got the same treatment. The `;` handling of wt itself stays the open ROADMAP item.
